### 2026-07-11 (post-merge) - Real Gemini call attempted with a live key: reached the API, failed on depleted account credits, not a code defect

- **Source:** human provided a real `GOOGLE_AI_API_KEY` (Google AI Studio) after story-01 had already merged to `develop` via PR #32, specifically to close Residual #1
- **Related story/task:** story-01-assessment-agent (post-closure verification)

- **Resolution:** treated this as valid, if incomplete, evidence. Decision: accept as sufficient — updated the story's Done Criteria #1 and Residual #1 to describe precisely what was and wasn't proven, rather than leaving the original "no key available" language standing now that a key was in fact used.
- **Tooling notes carried forward:** (1) the Bash tool's shell state does not persist across tool calls — an `export` in one call is invisible in the next; anything needing an env var across steps must set-and-use it within a single call. - **Retrospective signal:** when a live external-service smoke check fails, isolate whether the failure is inside your own code or upstream *before* concluding the check is blocked — an independent `curl` against the raw provider API with the same credentials separates "our integration is broken" from "the account/environment can't currently succeed," and only the former is actionable by fixing code. Documenting a deferred verification gap needs to be revisited (not just left as the original deferral note) once new evidence actually changes what's known, even if the new evidence doesn't fully close the gap.

### 2026-07-11 16:39 - task-05: writing the adapter test surfaced a real production bug (EmptyUsage vs null)

- **Source:** `/plan-task` execution, story-01-assessment-agent task-05, caught by a genuine test failure (`expected: null but was: 0`), not by inspection
- **Related story/task:** story-01-assessment-agent, task-03-assessment-agent-service (introduced the bug), task-05-unit-tests (caught it)
- **What happened:** `GeminiAssessmentGenerationAdapterTest.shouldReturnNullTokenFieldsWhenUsageMetadataIsUnavailable` (written per task-05's own spec: "when usage metadata is unavailable... token fields come back null") failed — the adapter returned `0`, not `null`. `GeminiAssessmentGenerationAdapter` checked `usage != null` to decide "unavailable," but Spring AI's `ChatResponseMetadata.getUsage()` never actually returns `null` — it defaults to `EmptyUsage`, a public marker class whose `getPromptTokens()`/`getCompletionTokens()` both return `0`. The null-check never fired in practice, silently reporting `0` estimated tokens (and, downstream, a non-null but wrong `costEstimate` of `0.0`) whenever a provider omitted real usage data, instead of the `null` the class's own contract and `AgentExecutionLogPayload`'s Javadoc promise.
- **Resolution:** changed the adapter's check to `usage != null && !(usage instanceof EmptyUsage)`. The test that caught this (constructing `ChatResponseMetadata` without calling `.usage(...)`, which is exactly how a real "no usage data" response looks) needed no change — it was already correctly modeling reality; the production code was wrong.
- **Retrospective signal:** this is the second time in this story that writing a *test* for behavior already implemented in a prior task caught a real bug the implementing task's own manual smoke-testing missed (see the `@ConditionalOnBean` entry from task-04). task-03's smoke check only exercised the happy path with real usage data present — the "metadata unavailable" branch was never actually exercised until task-05 wrote a test for it. When a task defers a specific test case to a later task (as task-03 did, deferring to task-05 by design), don't treat that branch as verified until the later task's test actually runs — the design intent being written down is not the same as it being checked.

### 2026-07-10 20:40 - task-04: @ConditionalOnBean(ChatClient.Builder.class) worked for the false case but silently broke the true case

- **Source:** `/plan-task` execution, story-01-assessment-agent task-04, caught via manual curl smoke testing (not by the test suite — `./mvnw -Pbeta test` stayed green throughout)
- **Related story/task:** story-01-assessment-agent, task-03-assessment-agent-service (introduced the pattern), task-04-internal-endpoint (exposed the bug)
- **What happened:** task-03 gated `AssessmentConfig` with `@ConditionalOnBean(ChatClient.Builder.class)` to keep `contextLoads` passing under the `test` Spring profile (which has no such bean). That looked correct — `contextLoads` passed, and a quick `beta` startup check with dummy Google GenAI config also started cleanly. task-04 added `AssessmentController` with the same `@ConditionalOnBean` guard, and its own `contextLoads` run passed too. But a `curl` smoke test against the running `beta`-profile app (dummy key, so `ChatClient.Builder` genuinely exists) returned **404 Not Found** — the controller's route was never registered, even though the bean it depends on existed.
- **Root cause:** `@ConditionalOnBean` on a *regular* component-scanned `@Configuration`/`@RestController` class is evaluated before Spring Boot processes auto-configuration classes (Spring AI's `GoogleGenAiChatAutoConfiguration`, which is what actually creates `ChatClient.Builder`) — auto-configurations run in a distinct, later phase specifically so *they* can safely condition on regular beans, not the other way around. So the condition was always evaluated as "bean absent," which happened to produce the right answer under `test` (truly absent) by coincidence, and the wrong answer under `beta` (present, just not yet at evaluation time).
- **Resolution:** replaced `@ConditionalOnBean(ChatClient.Builder.class)` on both `AssessmentConfig` and `AssessmentController` with `@ConditionalOnProperty(prefix = "app.agents.gemini", name = "enabled", havingValue = "true", matchIfMissing = true)` — a property condition, resolved from the `Environment` before any bean processing begins, with no ordering dependency on other configuration classes. Added `app.agents.gemini.enabled: false` to `application-test.yml` (documented inline, next to the existing Spring AI autoconfiguration exclusion it depends on). Verified with real HTTP requests against a running `beta`-profile instance (not just `contextLoads`): auth rejection (403), invalid-command rejection (422, full error body with log payload and correlation ID), and correlation-ID propagation on both accepted and rejected requests all behaved correctly.
- **Retrospective signal:** `contextLoads` passing is necessary but not sufficient evidence that Spring conditionals behave correctly — it only proves the *excluded* branch works, since that's the only profile the test suite runs under. The *included* branch (the actual production path) needs its own positive evidence, which for a web endpoint means an actual HTTP request, not just "the app started without an exception." `@ConditionalOnBean` targeting an auto-configuration-provided bean from a regular configuration class is a known Spring Boot pitfall — prefer `@ConditionalOnProperty` (or a real auto-configuration class with `@AutoConfigureAfter`) whenever the gating decision can be expressed as a property instead of a bean-presence check.
