### 2026-07-12 - task-03 code review: model field was accepted but silently discarded (P1), plus two documentation-durability gaps (P2, P3)

- **Source:** human code review (`.code-review/story-01-groq-provider-adapter/task-03-provider-selection.md`, PR #37), verified directly rather than accepted at face value, per `superpowers:receiving-code-review` discipline
- **Related story/task:** story-01-groq-provider-adapter, task-03-provider-selection
- **What happened (P1, confirmed real):** `AssessmentCommand.model` was exposed on the contract and documented as forwarded, but `AssessmentAgentOrchestrator` only ever passed `renderedPrompt` to `selected.port().generate(...)` — `AssessmentGenerationPort.generate(String)` had no way to receive a model at all. A request sending `"provider": "groq", "model": "some-other-model"` would silently run with the configured default instead, while looking like it had honored the override. Verified by inspecting the exact call site (`AssessmentAgentOrchestrator.java:76` at review time) before touching anything.
- **Resolution (P1):** confirmed via `javap` against the real installed Spring AI 2.0.0 jars that both `OpenAiChatOptions.Builder` and `GoogleGenAiChatOptions.Builder` inherit a concrete `model(String)` method from the shared `DefaultToolCallingChatOptions.Builder`, and that `ChatClient.ChatClientRequestSpec.options(B)` accepts that builder directly — so wiring a real per-call override was a small, contained change, not a reason to defer or de-scope the field (the two options the reviewer offered). Added `model` to `AssessmentGenerationPort.generate(String, String)`; both adapters now call `.options(GoogleGenAiChatOptions.builder().model(model))` / `.options(OpenAiChatOptions.builder().model(model))` when `model != null`. Verified two ways: a new unit test (`GeminiAssessmentGenerationAdapterTest.shouldForwardRequestedModelAsPerCallChatOptionsWhenModelIsProvided`, `ArgumentCaptor` on `requestSpec.options(...)`) and a real Groq call — default (no `model`) returned `log.model: "llama-3.3-70b-versatile"`; the same request with `"model": "llama-3.1-8b-instant"` returned `log.model: "llama-3.1-8b-instant"` — a clean differential proof the override reaches the real provider call. This does **not** reopen the model/capability registry question the human explicitly deferred earlier in this task's own review cycle (see the `AskUserQuestion` entry below, if present in this session) — no whitelist or validation was added, only the pass-through wiring the task's own Objective already claimed to deliver.
- **What happened (P2, confirmed real):** the cross-repo notification to `api/`'s `agentclient` planning existed only as a bullet inside `task-05-agentclient.md`'s Technical Design — not in the durable places `001`'s `previousDraft` precedent used (the story's own `Cross-repo dependency` line and its `Inconsistencies Found` table, plus a `TRACEABILITY.md` note). A future reader of `api/`'s active planning scanning only those durable locations would miss the contract change entirely.
- **Resolution (P2):** added a proper `Inconsistencies Found` row (mirroring the exact format of the existing `previousDraft` row), updated the story's `Cross-repo dependency` line to point at it, and added a note to `api/`'s own `TRACEABILITY.md` — all in the `api/` worktree, on its own branch, as a separate concern from `agents/`'s commit (per this repo's commit-scoping rule for cross-repo/child-planning changes).
- **What happened (P3, confirmed real):** `MANUAL-PROVIDER-TESTING.md` still described "before task-03 lands, this always routes to Gemini" as the current state, even on the branch where task-03 had already landed the selector.
- **Resolution (P3):** rewrote that section to describe actual current behavior (selector resolves `provider`, default `groq`, per-provider cost rate) and added inline `model`-override documentation to the curl example.
- **Retrospective signal:** the task's own Objective sentence ("...can specify which provider (and optionally model) to use") was accurate marketing copy for a mechanism that was only half-built — `provider` worked, `model` didn't, and nothing in the Verification table would have caught it since no verification row exercised a non-default `model` value. When a task's Done Criteria or Objective makes a specific claim, at least one verification step should exercise that exact claim, not just adjacent ones — the same lesson `001`'s P2 finding (curl vs. real `ChatClient` path) already taught, recurring in a new form.

### 2026-07-12 - task-03: real Gemini call reused 001's known quota-exhaustion signature; Groq real call succeeded and closed 001's Residual #1

- **Source:** `/plan-task` execution, story-01 task-03, real end-to-end smoke test (Implementation Step 7)
- **Related story/task:** story-01-groq-provider-adapter, task-03-provider-selection
- **What happened:** with no valid Gemini key available in this conversation, the human was asked (`AskUserQuestion`) how to proceed for Verification row 2 ("`provider: gemini` routes to Gemini"); chose to share a real Gemini key on the spot. A real end-to-end request with `provider: "gemini"` reached Gemini's real API but failed with `422 MALFORMED_OUTPUT` (`AssessmentAgentOrchestrator`'s generic "Failed to generate content" wrapper message, which does not surface the underlying HTTP status). Rather than accept the generic message at face value, made an independent direct `curl` to `generativelanguage.googleapis.com` with the same key — got the identical `429 RESOURCE_EXHAUSTED` / prepayment-credits-depleted response already documented in `001-assessment-creation/RETROSPECTIVE-RAW.md`. Confirms the key is real and valid but the same account's credits remain exhausted; the `422` was Spring AI correctly translating a real provider-side failure, not a routing or code defect.
- **Resolution:** treated as sufficient evidence for provider-routing correctness (proves the selector picked the `"gemini"` bean specifically — a different code path than the successful Groq call — and reached Google's real endpoint), same evidentiary tier `001` already accepted. The no-provider request (defaulting to Groq) succeeded fully: real `AssessmentResult`, `model: llama-3.3-70b-versatile`, `costEstimate: 0.0` — this is the first fully successful live-provider call observed in this project, closing `001`'s Residual #1.
- **Verification row 4 (costEstimate differs by provider) could not be closed empirically** for the same reason — no completed Gemini run exists to compare against a completed Groq run. Closed at the unit level instead: added `AssessmentAgentOrchestratorTest.shouldUseTheResolvedProviderOwnRateForCostEstimateNotAnotherProvidersRate`, which wires two mocked ports under two different provider names with two different configured rates and asserts identical token counts produce different `costEstimate` values matching each provider's own rate — isolates the exact claim (cost computation reads the resolved provider's rate) independent of live API availability. Also added `shouldThrowInvalidCommandWhenProviderIsUnrecognized` (unit-level regression coverage for the `validate()` branch this task added), since both are single, targeted additions tied directly to code this task introduces — not the comprehensive suite Done Criteria explicitly defers to task-04.
- **Retrospective signal:** a live-call failure's generic error message (Spring AI's own `"Failed to generate content"`) is not enough to distinguish "code is broken" from "provider quota is exhausted" — the same lesson from `001`, reconfirmed: always corroborate with an independent, minimal-surface probe (raw `curl` to the provider) before concluding either way. Real API keys shared in-conversation for this purpose were used only to populate a local, gitignored `.env` for the smoke test and were never logged, committed, or written to any planning/evidence file — swept the repo for both key values after cleanup to confirm no leakage.

### 2026-07-12 - task-02: task-01's OpenAI dependency already broke real app boot under `-Pbeta`, not just tests

- **Source:** `/plan-task` execution, story-01 task-02, discovered by actually starting the app (as task-02's own Risk row required) rather than trusting `./mvnw compile`
- **Related story/task:** story-01-groq-provider-adapter, task-01-groq-adapter (introduced the dependency), task-02-env-config (surfaced and fixed the boot failure)
- **What happened:** starting the app under `-Pbeta` with dummy Gemini config failed with `NoUniqueBeanDefinitionException` — Spring AI's `ChatClientAutoConfiguration.chatClientBuilder()` requires exactly one `ChatModel` bean, and with both `spring-ai-starter-model-google-genai` and `spring-ai-starter-model-openai` (added in task-01, for Groq) on the classpath, two exist (`googleGenAiChatModel`, `openAiChatModel`). This had already broken real `-Pbeta` boot since task-01 merged — the automated suite never caught it because `GradeOpsAgentsApplicationTest` runs under the `test` profile, where both providers' autoconfiguration is excluded and this bean never gets built at all.
- **Resolution:** excluded `ChatClientAutoConfiguration` in `application-beta.yml`/`application-demo.yml`; changed `AssessmentConfig.geminiAssessmentGenerationAdapter` to inject `@Qualifier("googleGenAiChatModel") ChatModel` (Spring AI's own bean name) and build the `ChatClient` directly via `ChatClient.builder(chatModel).build()` instead of the now-ambiguous autoconfigured `ChatClient.Builder`. Verified: app boots with only `.env` populated (no `export`), and a real request through `/internal/agents/assessment` still reaches validation correctly (403 without auth, 422 for a blank required field with a full failure-log payload) — the whole pipeline still wires end-to-end through the new qualified bean.
- **`.env` loading mechanism:** chose a custom `DotenvEnvironmentPostProcessor` (`shared/infrastructure/config/`, registered via `META-INF/spring.factories`) over a third-party dotenv library — no external dependency to verify/risk, full control over precedence (dotenv values are added as the lowest-priority property source, never overriding a real shell-exported var or `-D` system property). Reads `.env` from the working directory, skips comments/blank lines, strips surrounding quotes.
- **Retrospective signal:** a Maven-profile-gated dependency (`spring-ai-starter-model-openai` only in `beta`/`demo`, per task-01) can silently break a *real* startup path that no automated test exercises, because the test suite's own profile deliberately excludes the exact autoconfiguration that broke. `./mvnw test` passing is not evidence a Maven profile's actual runtime combination still boots — this is the same category of gap as `001`'s `@ConditionalOnBean` lesson (`contextLoads` passing proves the *excluded* branch works, not the *included* one), recurring here one layer up the stack (a whole starter's autoconfiguration, not one `@Conditional`). Task-02's own Risk row anticipated exactly this and required an empirical boot check before calling the task done — that check is what caught it, not the test suite.

### 2026-07-12 - task-01 code review: two real findings — OpenAI autoconfig broke contextLoads, and curl evidence didn't prove the real ChatClient path

- **Source:** human code review (`.code-review/story-01-groq-provider-adapter/task-01-groq-adapter.md`, PR #35), then verified directly rather than accepted at face value, per `superpowers:receiving-code-review` discipline
- **Related story/task:** story-01-groq-provider-adapter, task-01-groq-adapter
- **What happened (P1, confirmed real):** `./mvnw -Pbeta test -Dtest=GradeOpsAgentsApplicationTest` failed with `BeanCreationException` — adding `spring-ai-starter-model-openai` (for Groq) put OpenAI's six autoconfiguration classes (`OpenAiChatAutoConfiguration`, `OpenAiAudioSpeechAutoConfiguration`, etc.) on the classpath, and none had credentials under the `test` Spring profile, unlike Google GenAI's which are already excluded there. Reproduced exactly as the reviewer described before touching anything.
- **Resolution (P1):** added all six OpenAI autoconfiguration classes to `application-test.yml`'s `spring.autoconfigure.exclude` list, mirroring the existing Google GenAI exclusions. Verified with the reviewer's exact command (`-Dtest=GradeOpsAgentsApplicationTest,GeminiAssessmentGenerationAdapterTest` → `BUILD SUCCESS`) and the full suite (18/18).
- **What happened (P2, confirmed real and deeper than expected):** the reviewer noted `task-01-groq-structured-output-evidence.md` used raw `curl`, not the actual `ChatClient.responseEntity(AssessmentResult.class)` Java path the task claims to have validated. Verifying this properly (a scratch `ApplicationContextRunner` test building a real `ChatClient` via `OpenAiChatAutoConfiguration` pointed at Groq) revealed the raw-curl evidence had been **hiding a real failure**: `llama-3.1-8b-instant` — the model used throughout this story's examples — returns `HTTP 200` but echoes the JSON Schema itself back as the response content when called through `responseEntity(Class)`, instead of data conforming to it, because Spring AI's `BeanOutputConverter` builds a different (schema-embedding) prompt than the raw curl's explicit field-by-field instruction did. `AssessmentResult` came back with every field `null`/empty. Retrying with `llama-3.3-70b-versatile` (same test, same prompt, only the model changed) succeeded correctly.
- **Resolution (P2):** corrected every reference to `llama-3.1-8b-instant` as the example/default Groq model (`MANUAL-PROVIDER-TESTING.md`) to `llama-3.3-70b-versatile`. Rewrote `task-01-groq-structured-output-evidence.md`'s Conclusion to state plainly that the mapping code itself is correct but the model choice matters, with both the failing and passing real-`ChatClient` transcripts committed as evidence. Also confirmed empirically, as a side effect of building the real `ChatClient`, that Groq's OpenAI-compatible base URL needs the `/v1` suffix (`https://api.groq.com/openai/v1`) — a bare `https://api.groq.com/openai` 404s (the scratch test's first attempt used the bare form and failed this way before being corrected); task-02's already-planned `GRADEOPS_GROQ_BASE_URL` default was written with `/v1` from the start and needed no change.
- **Retrospective signal:** a raw-curl call and a `ChatClient.responseEntity(Class)` call can use entirely different mechanisms to reach "structured JSON" (explicit prompt instructions + basic `response_format: json_object` vs. Spring AI's own schema-embedding `BeanOutputConverter` prompt) — passing one is not evidence the other passes, especially for a smaller/faster model whose instruction-following is weaker than its raw JSON-mode compliance. When a task's Done Criteria claims a specific code path was validated, verify that exact path, not an adjacent one that happens to be easier to script. The reviewer's insistence on this distinction (P2) surfaced a real, previously-invisible model-selection bug, not just a documentation nit — validates the "verify before implementing, don't performatively agree" discipline even (especially) when the initial fix looks like it satisfies the letter of the feedback.
- **Follow-up (human direction):** the scratch verification test was originally planned for deletion after capturing evidence. Human explicitly asked to keep it instead — useful going forward to re-validate provider communication on demand whenever Groq's behavior, the chosen model, or the Spring AI version changes, without needing to re-derive the `ApplicationContextRunner`/autoconfiguration wiring from scratch each time. Kept as `GroqChatClientManualVerification` (renamed from `...ScratchVerification` to reflect its permanent role), made reusable: `GROQ_MODEL` is now an overridable env var (default `llama-3.3-70b-versatile`) instead of hardcoded, it skips gracefully via `Assumptions.assumeTrue` when `GROQ_API_KEY` isn't set rather than failing, and it asserts the mapped result is actually populated (not just prints it) so a run gives a clear pass/fail, not only text to eyeball. Confirmed the filename still keeps it out of Surefire's default `**/*Test.java`/`Test*.java`/`**/*Tests.java` include patterns, so `./mvnw test` doesn't pick it up automatically — full suite re-verified at 18/18 after the rename.

### 2026-07-12 - task-01: Groq project had every chat model blocked by default; resolved by enabling one in the console

- **Source:** `/plan-task` execution, story-01 task-01, real Groq API verification call (Implementation Step 3)
- **Related story/task:** story-01-groq-provider-adapter, task-01-groq-adapter
- **What happened:** the first real verification call against Groq (needed to settle R-01 — whether structured-output mapping works) returned `403 model_permission_blocked_project` for `llama-3.3-70b-versatile`. Assumed initially this was a per-model restriction and tried 5 more models (`llama-3.1-8b-instant`, `openai/gpt-oss-20b`, `meta-llama/llama-4-scout-17b-16e-instruct`, `qwen/qwen3-32b`, `allam-2-7b`, `groq/compound`) — every one returned the same error (`groq/compound`, an agentic/compound system, surfaced the error from the underlying model it routed to internally). All 6 attempts were real HTTP round trips with real error responses, not client-side failures — this is an account/project configuration state (the Groq project had zero models enabled by default), not a code or design defect, same category of finding as `001`'s Gemini-credits situation.
- **Resolution:** asked the human explicitly rather than guessing further or silently accepting a blocked-evidence gap; human enabled `llama-3.1-8b-instant` via `console.groq.com/settings/project/limits` and the same request succeeded (`200`, valid JSON matching `AssessmentResult`'s schema exactly). See `task-01-groq-structured-output-evidence.md` for the full request/response.
- **Retrospective signal:** a new Groq project key has no models enabled by default — this needs to be called out wherever the Groq API key setup gets documented for other environments (e.g. Cloud Run provisioning in story-02, or onboarding notes for a future teammate), so nobody else loses time thinking it's a code bug when it's project configuration. Same pattern as `001`'s Gemini-credits lesson: isolate whether a live-API failure is inside the code or upstream *before* concluding the integration itself is broken.
